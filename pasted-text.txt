# AI-SOC — AI-Powered Security Operations Center

## 1. Project Goal

Build a production-style Security Operations Center platform that:

1. Ingests security telemetry.
2. Normalizes events into a common schema.
3. Detects suspicious behavior using deterministic rules.
4. Correlates related events into incidents.
5. Uses machine learning to detect anomalous behavior.
6. Maps suspicious behavior to MITRE ATT&CK techniques.
7. Uses LangGraph-powered AI investigation workflows to analyze incidents.
8. Produces human-readable explanations and remediation recommendations.
9. Provides a real-time SOC dashboard.
10. Runs locally with Docker Compose.
11. Deploys cheaply to AWS using primarily one EC2 instance.
12. Provides measurable security/ML/system benchmarks.

The application is a defensive cybersecurity project. Attack telemetry should come from public datasets, synthetic event generation, or an isolated lab environment owned by the developer.

# 12. Initial Detection Rules

Implement at least these.

## Rule 001 — Brute Force

Condition:

Multiple login failures from the same source IP inside a defined time window.

Configurable:

```text
threshold = 10
window = 60 seconds
```

---

## Rule 002 — Password Spray

Condition:

One source IP attempts authentication against many usernames.

Example:

```text
source_ip = same
unique_users >= threshold
within 5 minutes
```

---

## Rule 003 — Impossible Authentication Pattern

For MVP, simulate a simplified version.

Detect:

```text
same user
different countries
very short time interval
```

Do not attempt precise geospatial travel calculations initially.

---

## Rule 004 — Suspicious Privilege Change

Trigger when:

```text
privilege_change
```

occurs shortly after unusual authentication.

---

## Rule 005 — Large Download

Trigger when:

```text
bytes_received/downloaded > configured threshold
```

---

## Rule 006 — Login After Brute Force

Correlate:

```text
many failed logins
        ↓
successful login
```

Raise severity significantly.

---

## Rule 007 — New Device Login

If known-device tracking exists:

```text
user logs in from previously unseen device
```

# RULES CODEX MUST FOLLOW

1. Implement one sprint at a time.

2. Do not implement future sprint functionality unless required by the current sprint.

3. Do not replace deterministic security logic with LLM calls.

4. Keep business logic out of FastAPI route handlers.

Routes should look approximately like:

```text
request
 ↓
validation
 ↓
service
 ↓
repository/domain
 ↓
response
```

5. Use async I/O where appropriate.

6. Use typed Python.

7. Add tests with every feature.

8. Every database schema change must use Alembic.

9. No hardcoded API keys or passwords.

10. Use dependency injection where useful.

11. AI output must use structured schemas.

12. Long AI tasks must execute through workers.

13. Do not make LLM availability a requirement for event detection.

14. Do not make ML availability a requirement for rule detection.

15. Keep modules loosely coupled.

16. Use PostgreSQL as the source of truth.

17. Redis should contain temporary/cache/queue data, not critical permanent records.

18. Log important operations.

19. Every alert must contain evidence explaining why it triggered.

20. Every incident should be explainable without AI.
